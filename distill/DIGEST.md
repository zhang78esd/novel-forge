# 九个开源写小说 Skill，蒸馏成一个：精华长文

> 蒸馏日期：2026-11-07 · 方法：仓颉 skill v2.5（RIA-TV++ / single 编译）· 语料：9 个仓库、144 个 Markdown 文件
> 产物：`novel-forge/`（1 个 SKILL.md + 15 张能力卡 + 索引/速查/术语/概览）

## 一、为什么要把九个合成一个

上一轮排名的结论是：`oh-story-claudecode` 一家就有 14 个 skill，`chinese-novelist-skill` 有 9 个流程文档，`sumeru` 有 8 个，`story-skills` 有 24 个。九源加起来上百个入口。

仓颉 v2.5 的实测数据说明了问题：19 个平铺技能，光「技能名＋描述」的发现目录就要 3,897 tokens，每轮对话都跟着走；收敛成 1 个路由入口后是 340 tokens。装的时候很爽，用的时候想不起来该调哪个——这是技能库变胖之后最真实的成本。

更要命的是**触发竞争**：用户说「帮我接着写」，`state-ledger`、`continuation`、`parallel-writing` 三个都会觉得自己该上。所以这次不是把九份文档拼接，而是把它们拆成互不重叠的能力卡，用一个路由表按意图只加载 1 张（跨域最多 2 张）。

## 二、九源真正的共识：长篇是工程问题，不是文笔问题

这是蒸馏中最意外的发现。九家写法各异，但 strongest agreement 落在三条与文笔无关的机制上：

**1. 发生过的事实必须有唯一底账。**
`webnovel-writer` 把文件分成写前真源（大纲、设定、禁区）、写后真源（已定稿章节 + `CHAPTER_COMMIT`）、投影层（state、索引、摘要、向量库、Dashboard）。投影层全部自动生成、禁止手改、禁止当事实源。`oh-story` 把 `_tracking-state.json` 定为「唯一底账」，`Novel-Control-Station` 要求每章被接受后强制回写动态状态，`wordflowlab` 用 9 项写前重读清单防止长对话丢失早期设定。

四家独立实现同一件事，说明长篇崩坏的根因不是模型变笨，是「事实没有权威记录」。换会话、换 Agent、写到第 200 章，都靠文件恢复。

**2. 要维护两条时间线，不是一条。**
`oh-story` 叫「作者真相 / 读者已知」，`chinese-novelist` 做成四栏设定词典（名词｜首现章节｜读者已知｜完整真相｜计划揭示），`story-skills` 用 `reader-knowledge` 标记过滤上下文。三家说的是同一件事：**角色不能说破自己不可能知道的事，叙述者不能提前把伏笔解释掉**。

配套的一条洞察很锋利：「悬念是读者知道该问什么，困惑是读者连这个词是什么都不知道——后者不是留白，是阅读噪音。」所以设定名词首现必须给「类别＋一个可感知特征」。

**3. 去 AI 味不是二选一。**
`oh-story` 的 `story-deslop` 是分层而非站队：`check-ai-patterns.js` 这类确定性 lint 逐条匹配已知句式模板、给行号和改写方向，只负责**定位硬伤**（blocking 清零或白名单）；表达/用笔/故事三层扫描负责**语义读感**（advisory 回语境判断）。原话是「零命中不代替三层扫描」「不为归零机械改稿」。

`human-writing` 补上了最狠的一刀：判定要按**动作**而非字面。它把「不是A，而是B」「不在于A，而在于B」「你以为A，其实B」统称为「翻案腔」——先立一个读者并没有的误解，再推翻它抬价。因为按字符串禁令，模型会换皮绕过。

而两边共同禁止的是**靠加戏制造真人感**：不许新增摔杯、攥袖、锁门、粗话、旁人吃惊来掩盖因果空洞。`Novel-Control-Station` 则警告不要「盲洗」把时代质地、题材语域、人物声音一起洗平。

## 三、把「不好看」拆成可定位的故障

`chinese-novelist` 的钩子十三式、章首引子七式、三段式播种—生长—收获，是九源里最完整的可执行行文方法。但更有价值的是它的**禁忌清单**，因为禁忌比技巧更能定位问题：

- 虚假悬念：「他听到了脚步声……原来是猫」
- 机械降神：「她突然想起自己会武术」（对比：她想起第五章父亲教过的防身术）
- 过度留白：每章至少答一个旧悬念，再提新悬念
- 同质悬念：连续几章都用同一种钩子
- 低风险钩子：「他不知道晚饭吃什么」

加上 `sumeru` 的六类底线问题（时间线矛盾 / 设定崩坏 / 人物 OOC / 重复情节 / 信息泄露 / 伏笔死结）和 `Chinese-WebNovel-Skill` 的每章四问（想做什么 / 谁阻止 / 局面变成什么 / 为什么还往下看），「读者不追了」就从一句模糊反馈变成了可定位的四类故障：追读故障、阅读噪音、注水拼接、长篇崩坏。

三条跨章悬念弧（短 2–3 章 / 中 5–8 章 / 长弧全书）要同时跑；「读者翻开下一章的理由，永远要在这一章的结尾给够，一次只留一个悬念不够」。

## 四、两条容易打起来的规则，以及怎么裁决

蒸馏时发现一处表面冲突：

- `chinese-novelist`：第三、四阶段「所有过程都禁止向用户确认」。
- `oh-story`：裸调用「不得自动进入正文写作，也不得把已有项目默认为日更 3 章」。

其实不矛盾，是两句话管的阶段不同：**模式与章节范围必须显式确认；确认之后，逐章过程不再打断**。`Novel-Control-Station` 的疯狂创作模式把这条写全了：「不再逐章问用户，但每章内部控制步骤一个都不能少」。

裁决结果落在 `parallel-writing`：含糊指令只诊断并列选项，不默认日更 3 章，单轮正文 ≤3 章；开启无人值守后，写前必读、一致性检查、状态回写、去味、审查一步不省。

## 五、这份产物刻意没做什么

- **不绑脚本。** 九源里大量机制绑在特定脚本（`tracking_commit.py`、`check-ai-patterns.js`、`validate-timeline.py`）。本包抽的是机制，卡片的 E 段给了无脚本时的降级约定：例如退化为「单一手写底账文件 + 每章回写」，但仍保证只有一个写入口。
- **不把经验值当定律。** 「每 3–5 章一个小爽点」「遗忘阈值 10/12/20 章」都是经验参数，标注为诊断工具，不作硬配额。仓颉自己的方案文档也批评过「没有基线就拍脑袋定阈值」。
- **不覆盖短篇。** 九源里 7 个面向百万字网文，短篇被当附属。故单列 `short-form-emotion`：「短篇以情绪为目标，所有内容为情绪服务」，不套卷纲、黄金三章与多弧并行；场景完成职责就收，不加戏凑长度。
- **不碰版权表达。** 拆文只迁移抽象机制：专名换功能位占位符，情节改写成「动作＋结果＋代价」，最长连续重合 ≤12 字。导入源与对标书硬隔离，避免自我抄袭。
- **不承诺「过检测」。** 外部 AI 检测器只作自测参考，不替代人工读感。

## 六、怎么用这个 skill

装到 Agent 的 skills 目录后，直接说需求即可，路由表会只加载 1 张卡：

| 你说 | 加载 |
|---|---|
| 「我有个点子，想开本新书」 | `project-bootstrap` |
| 「写到第 30 章设定对不上了」 | `state-ledger` |
| 「这段太像 AI 写的」 | `deslop` |
| 「为什么没人追」 | `failure-patterns` |
| 「导入前面写的 20 章」 | `import-legacy` |

概览类问题只读核心原则，不加载任何卡。路由表命中不了就明确说超出范围，不硬套。

## 七、诚实的账：收敛入口省了什么、又重了什么

仓颉自己的方案文档把这笔账写得很直白，这里照抄立场：**入口小了，命中变重了**。

- 省的是目录：1 个入口 vs 上百个 skill 名与描述，每轮对话不再背一长串互不区分的名字；也消除了触发竞争。
- 重的是单次命中：走路由要先读 SKILL.md，再读能力卡，比直接命中一个原子 skill 多一段路径。
- 所以收益是**产品收益（认知负担、可维护性）**，不是纯粹的 token 收益。别把这两笔账混着承诺。

另一个诚实边界：本次触发评测是关键词/意图级的确定性匹配，不是多模型盲测；输出评测只覆盖 2 个代表任务。详见 `trigger-evals.md` 与 `output-evals.md`。按仓颉的评测纪律，基线出来之前不宣称「全部通过」，只报告实际跑了什么。
