# 阶段 0 — 整书理解（Adler 四步）

对象：GitHub 写小说 Skill 榜单九源资料集（9 仓库 / 144 个 .md / 约 1 MB）。
完整版（含批判与应用）见 `bundle/book/overview.md`；本文为阶段 0 的流水线留档。

## 1 结构：这份资料集讲什么

九源共同回答「怎么让 AI 稳定写完一部长篇」，按创作时序可分为七段：选题 → 定位 → 拆解 → 大纲 → 逐章写作 → 状态/一致性维护 → 审查与去味。另有三条横切能力：断点续写、并行连写、逆向导入旧稿。

彼此不是九个替代品，而是互补：oh-story 提供全链路与去味 lint；chinese-novelist 提供行文技法与钩子库；webnovel-writer / sumeru / Novel-Control-Station 提供长篇工程；story-skills / wordflowlab 提供一致性与承诺追踪；human-writing 提供中文语感硬规则；Chinese-WebNovel-Skill 提供按需单层精修。

## 2 解释：核心论点

**长篇质量是事实管理问题，不是文笔问题。** 四源独立实现「每章写后强制回写状态」，三源独立实现「作者真相/读者已知分离」，三源独立实现「去味不能靠加戏」。这三组跨源共识构成本次 Bundle 的骨架。

**入口要少、能力要多。** 九源共 100+ 个 skill，平铺安装带来目录膨胀与触发竞争；用户明确要求合成 1 个 skill，与仓颉 v2.5 的 single-first 原则一致。

## 3 批判：盲点与冲突

| 问题 | 表现 | 本次处理 |
|---|---|---|
| 工具绑定过强 | 机制绑在特定脚本与目录名 | 抽机制，卡片给无脚本降级约定 |
| 长篇偏向 | 7/9 面向百万字网文 | 单列短篇卡，长篇卡 B 段写明短篇不适用 |
| 无基线的量化阈值 | 爽点密度、遗忘阈值、AI 率 | 标为诊断参数，不作硬配额，不承诺过检 |
| 表面冲突 | 「禁止确认」vs「裸调用不得自动开写」 | 判定为阶段不同，统一到 parallel-writing |
| 版权风险 | 拆书/仿写容易滑向换皮 | 占位符抽象＋连续重合限制＋导入与对标硬隔离 |

## 4 应用：交付形态

- 输出模式：single（用户显式指定），1 个路由入口 + 15 张 RIA++ 能力卡 + 索引/速查/术语/概览。
- 加载规则：每次 1 张，跨域最多 2 张；概览类不加载卡。
- 晋级门：15 项全部 destination=router，无独立 Skill。
- 使用目的：workflow（接入日常创作工作流）。

## 阶段 0 用户确认点

按仓颉 SOP，阶段 0 后应向用户确认「骨架理解是否正确、有无重点方向」。本次用户在初始请求中已明确「蒸馏成一个新的 skill」，骨架与交付形态均有明确依据，故按 Agent 模式直接推进；用户可在看到 DIGEST.md 后要求调整能力划分或补充某个来源，Bundle 支持断点续跑与增量更新（改 verified.yaml 后重新 compile 即可）。
