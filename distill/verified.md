# 阶段 1.5 三重验证记录

验证口径（仓颉 v2.5 `03-stage1.5-triple-verify.md`）：

- **V1 来源充分性**：可定位原文足以支持限定范围内的做法（完整机制在一处讲透也可通过）。
- **V2 可执行性**：用合法的新输入能完成任务并核验结果。
- **V3 任务增益**：能减少遗漏、统一口径或稳定交付；不要求作者独创。

分级：`verified`（编译为 active 能力）/ `reference`（并入 overview 或 glossary）/ `needs_review` / `rejected`。

## rejected — 淘汰项及原因

| 候选 | 淘汰原因 |
|---|---|
| 「一键生成封面图」 | 非文字创作，且依赖外部图像模型，V2 无法在本包内核验 |
| 「扫榜脚本实时采集榜单」 | 依赖特定平台与脚本，产物不附带脚本；V1 可定位但 V2 不可执行，降级为 trend-scan 中的可选步骤并声明数据缺口 |
| 「多 Agent 通讯 / Agent Teams」具体实现 | 绑定特定宿主能力，抽象为 parallel-writing 的模式选择即可 |
| 「仿写某本具体作品风格」 | 触及版权表达复刻，直接拒绝 |
| 「AI 生成声明合规 / 平台过稿规则」 | 平台政策随时间变化，无稳定方法论，V3 增益不可验证 |
| 「字数统计脚本 / 时间线校验脚本」本体 | 只保留「必须由确定性脚本判定」这一规则，脚本本体不迁移 |
| 「RPG 式选择交互推进剧情」 | 仅 1 源提及且无完整机制，V1 不充分 |
| 「把小说改编成可玩游戏」 | 超出文字创作范围，overview 中列为 out_of_scope |

裁决说明：`reference` 与 `needs_review` 项均未被伪装成 active 能力；`rejected` 保留在 `rejected/` 目录供审计。

## 阶段 1.6 晋级门

用户明确要求「蒸馏成一个新的 skill」，按 single-first 原则，15 项全部 `destination: router`，无一项晋级独立 Skill。五条判据评审：

- 独立意图 ✗：写小说各能力高度依赖同一项目文件链，用户几乎不会脱离创作流程单独请求某一环。
- 独立契约 ✓、独立运行 ✗：卡片有完整输入/输出/完成标准，但运行依赖项目目录与底账。
- 独立复用 ✓、独立评测 ✓。

前三条未全过 → 不晋级。未晋级项不淘汰，全部保留在来源路由入口内，可经路由表到达。可发现入口数 1，远低于软预算 8。
