# 扫榜选材：找重复模式，不追单本爆款

## R — 原文 (Reading)

> 核心信念：单本排名提供线索，近期多榜单、多作品的重复模式才支持趋势判断。
>
> — `zenstory-ai/oh-story-claudecode/skills/story-long-scan/SKILL.md`·导语·核心信念

> 不为填字段虚构事实，不把结果倒推成人物早有计划。
>
> — `zenstory-ai/oh-story-claudecode/skills/story-long-analyze/SKILL.md`·分析边界

## I — 方法论骨架 (Interpretation)

选题的证据等级：单本爆款只是线索，多榜单、多作品在近期重复出现的结构才是趋势。所以扫榜的输出不是「哪本火」，而是「哪类开局/人设/爽点结构在反复出现，以及它为什么成立」。

操作上把采集与判断分开：脚本/检索负责采榜单数据并做聚合，主会话只读聚合结果，避免把几十万字原文塞进上下文；判断阶段必须给每个维度写理由，评分不代替解释。聚合结果落盘成选题决策文件，后续拆文与写作从文件接上，不靠对话记忆。

## A1 — 应用案例 (Past Application)

**原仓库案例**：`oh-story-claudecode/README.md`「拆文报告：评分要给得出理由」给出结论样例——「三章是『立人设强、给爽点零』的极端结构。直接照搬会劝退番茄读者，但拆出来的局部技法（导师代言设定、延迟点名、身体反应外化）高度可复用。」这说明扫榜/拆文产出的是「可迁移的抽象机制」而非「照搬的书单」。

**合成演练**：三个平台近 30 天榜单聚合 → 发现「开局即被剥夺身份」在 7 部不同题材作品里重复出现 → 写选题决策：可迁移机制是「先剥夺再赋权」，不可迁移的是具体门派/职业设定。

## A2 — 触发场景 (Future Trigger) ★

### 情境
1. 开书前不知道写什么题材，想看市场在要什么。
2. 有一个点子，想验证它是不是已经过热或过冷。
3. 需要解释「为什么这本书能火」，用于自己的结构调整。
4. 平台换频道，要重新校准开篇节奏。

### 语言信号
- "现在什么题材好写 / 扫一下榜单 / 帮我选题"
- "这个点子有市场吗 / 会不会太套路"
- "拆一下这本爆款为什么火"
- "what's trending / analyze why this novel works"

### 与相邻能力的区分
- 与 `project-bootstrap`：本卡回答「市场要什么」，随后由定位卡回答「我要写什么」。
- 与 `deconstruct`：本卡扫「多本书的横向模式」，`deconstruct` 拆「单本书的纵向机制」。
- 与 `outline-architecture`：本卡不产出章节结构，别在这里排爽点。

## E — 可执行步骤 (Execution)

### 输入契约
必需：目标平台/频道、时间窗口（默认近 30 天）、篇幅线（长篇/短篇）。
若无实时榜单数据，明确声明「仅基于已有语料做结构分析」，不得伪装成实时趋势。

### 步骤
1. **定范围**：平台、频道、时间窗、样本量。完成标准：至少 2 个榜单来源或明确标注单源局限。
2. **采集与聚合**：名单、排名、题材标签、开篇钩子类型聚合成表。完成标准：主会话只读聚合表，不逐本读全文。
3. **找重复模式**：统计题材、开局、人设功能位、爽点间隔的重复项。完成标准：每个结论至少 3 部独立作品支撑，并写出「为什么成立」。
4. **写选题决策**：可迁移机制 / 不可迁移专名 / 风险提示 三段。完成标准：不含具体书名的专有设定作为待用素材。
5. **落盘交接**：写 `选题决策.md`，交给拆文或大纲。完成标准：下游可直接从文件读取，不依赖会话上下文。

### 输出契约
一份选题决策文件 + 一张重复模式表。判停：用户只想聊某本书好不好看时不启动采集，直接说明超出范围。

## B — 边界 (Boundary) ★

- **不要**把单本排名当趋势：这是原仓库写死的「核心信念」。
- **不要**虚构数据或把结果倒推成「人物早有计划」；缺失处写「未知」。
- **不要**照搬专有设定、角色组合、标志性场面或原句——只迁移抽象机制。
- 无实时数据访问能力时，如实说明数据缺口，不要用记忆编榜单。
- 短篇扫榜看的是六种目标情绪，不套用长篇的「黄金三章」模型。
